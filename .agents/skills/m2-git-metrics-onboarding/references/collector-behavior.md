# What The Collector Actually Transmits

Scope: the collector's real payload, and the four places where its own
documentation understates it. Load this module on every issue pass - the
disclosure paragraph in the install handoff is built from it, and it is
what makes the difference between informed and uninformed onboarding.

Established by reading the collector source and the app's own published
API description, not from the collector's README.

## Submission Shape

One run submits one POST per project to the app's metrics-submission
endpoint, authenticated with the per-(person, project) key as a bearer
token.

Envelope: collector version, schema version, period start, period length
in days, repository count, and a list of contributors.

Per contributor: the contributor's git display name; whether they were
configured or auto-discovered; commit count; insertions; deletions; PR
count; individual PR sizes and their average; a tally of file extensions
touched; a 24-bucket distribution of work hours; weekly and daily commit
counts; individual cycle times; a review-hygiene split of
via-merge versus direct; and a churn percentage.

## The Collection Scope Is Everyone, Not The Operator

Every code path records every contributor found in the discovered
repositories, regardless of whether that contributor matches the person
running it. There is **no configuration switch** limiting collection to
the operator's own commits.

The practical consequence: a person onboarded onto this tool is not
submitting data about themselves. They are submitting a named activity
profile of every person who has committed to the repositories in scope -
teammates, client-side staff, third-party vendor engineers, past
contributors. None of them are asked. This is the fact gate item 1 exists
to get authorized and the fact the handoff's disclosure paragraph must
state plainly.

## Four Documentation Gaps

The collector's README makes claims that the implementation and the app's
own API description contradict. All four matter for disclosure, because a
person who reads only the README will consent to something narrower than
what happens.

1. **"Anonymised before any AI summary sees them" is true but much
   narrower than it reads.** The app's own API description says so
   explicitly: the real name is kept, and anonymisation happens only at
   the boundary with the LLM summariser. Names are stored, and names are
   shown in the app's UI.

   Verified end to end on a real report: the generated prose referred to a
   peer as "Peer 1", while the dashboard table immediately above it named
   that peer and displayed their churn percentage, off-hours share and
   cycle time, alongside stored prose characterising the quality of their
   work. That peer had never opted in. The anonymisation is real; it just
   protects nothing that a reader of the page can see.

2. **An empty git author name causes the email address to be
   transmitted.** The contributor label falls back to the email when the
   display name is empty, so the README's "never sends email addresses"
   holds only for correctly configured git identities. A repository with
   one badly configured author is enough to break it, and nothing in the
   collector warns that it happened.

3. **File extensions are transmitted but undocumented.** The extension
   tally is in the payload and absent from the README's list of what gets
   sent, which claims no file names are transmitted. Extensions are not
   file names, but they are more than nothing - they characterise what
   kind of work a person does, and their absence from the documented list
   means nobody consented to them.

4. **Work-hour distribution is a behavioural profile.** A 24-bucket hourly
   histogram plus weekly and daily commit counts is enough to infer
   working patterns, and the app surfaces an off-hours share derived from
   it. This is documented, but its sensitivity is not - it reads as a
   technical metric and functions as a monitoring one.

## How The App Uses What It Receives

- An organisation-wide admin table with per-employee anomaly chips,
  including the "Direct to main" and "Large PRs" chips. Two of these are
  unreliable by construction - see `collector-bugs.md`.
- A per-employee risk level (green/yellow/red) with an internal note
  field, and a per-project team-health timeline.
- A scheduled weekly sweep that auto-generates any missing reports, so a
  submission produces a stored report whether or not anyone asks for one.
- Reports are generated by an external LLM (a Gemini-family model
  observed) and stored as rendered HTML.
- An activity-bonuses section sits adjacent to the git-metrics section in
  the admin area. Whether it consumes these submissions was not
  established - this is gate item 3.

Two things follow for M2. First, the app is labelled a proof-of-concept
build, and its API is reachable without authentication for schema reads;
treat its storage as less durable and less private than a production
system. Second, a submission is not inert - it produces stored, named,
LLM-written characterisations of people on a weekly cadence with no
further human action, which is why verification (workflow step 6) is
about knowing what exists, not just confirming a key works.

## The Deployment Advice That Needs A Decision, Not A Workaround

The collector's own install guide tells operators to keep the collector
out of the client repository, to hide it using a `.gitignore` at the
parent level rather than the client's own, and to turn the client VPN off
before submitting.

Each instruction is individually defensible - a metrics tool genuinely
should not be committed to a client repository, and a corporate VPN
genuinely can block an outbound call. Together, and combined with stored
real names of client-side contributors, they describe collection the
client is not meant to notice.

Do not reproduce this advice in an install handoff as neutral setup steps.
Where a step is genuinely needed (keeping the tool out of the client
repository), state the real reason. Where a step exists to route around
the client's own network controls, it is not a setup detail; it is part of
what gate item 1 has to authorize.
